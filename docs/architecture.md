# Архитектура LeadHelper

## Границы слоёв

| Каталог                                  | Ответственность                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `backend/cmd/server`                     | Composition root, конфигурация окружения, сборка зависимостей, HTTP lifecycle                    |
| `backend/internal/domain`                | Сущности Task, Member, Note, Message, Settings, SyncLog и структуры отчётов                      |
| `backend/internal/ports`                 | Контракты Repository, TaskSource, MailProvider, IncrementalMailProvider, BlobStore               |
| `backend/internal/application`           | Валидация, права модулей, разделение режимов, CRUD, отправка, синхронизация, отчёты              |
| `backend/internal/adapters/httpapi`      | HTTP routing, JSON decoding, лимиты, заголовки, экспорт, раздача SPA                             |
| `backend/internal/adapters/storage`      | SQLite, индексированные страницы почты и задач, DPAPI; JSON-адаптер для тестов и совместимости |
| `backend/internal/adapters/integrations` | Jira Cloud, IMAP, Microsoft Graph; транспорт, пагинация и маппинг                                |
| `backend/internal/adapters/mailformat`   | MIME / EML import и export                                                                       |
| `frontend/src/app`                       | Оболочка, навигация, серверное состояние, notifications                                          |
| `frontend/src/shared`                    | DTO, API-клиент, даты, общие элементы интерфейса                                                 |
| `frontend/src/features`                  | Независимые экраны dashboard, tasks, planner, team, mail, notes, reports, settings, integrations |

Порты направлены внутрь приложения; реализация не выбирается из use case. Замена хранилища или почтового провайдера происходит в composition root. Общие сущности намеренно небольшие: сервер не знает компоненты React, фронтенд не знает формат файла хранилища.

## Транзакции и отказоустойчивость

Основной адаптер — SQLite с WAL и сериализацией локальных транзакций записи. Почта хранится отдельно от документа рабочего пространства. Из основного документа задач транзакционные триггеры строят `task_rows` и небольшой `workspace_shell`; изменение только плана или настроек не перестраивает индекс задач. Пагинация, поиск и агрегаты читают индексированные строки без десериализации полного архива задач в приложении. Запись задач и синхронизация пока обновляют основной документ целиком.

`GET /state` получает небольшой снимок, агрегаты и ограниченные превью. Полная карточка читается отдельно; изменение статуса использует отдельный PATCH и не стирает отсутствующее в превью описание. План дня хранится отдельно от полей Jira и допускает несколько дат одной задачи. Сохранение одного дня проверяет ревизию ячейки и атомарно заменяет выбор; устаревшая запись получает 409.

JSON-адаптер для тестов получает копию состояния под write lock, выполняет callback и сохраняет файл через rename. Ошибка callback или записи в любом адаптере сохраняет прежнее состояние. Повреждённое хранилище не заменяется сидом.

Это однопроцессная реализация: mutex не координирует несколько серверов. Не запускайте две реплики на одном volume. Для общей многопользовательской установки нужны нормализованная запись, аутентификация, роли и разделение пространств.

Синхронизация не держит блокировку хранилища во время сетевого запроса. Результаты каждой попытки сохраняются в журнале. При смене режима или отключении провайдера во время запроса результат не применяется. Импорт идёт одной транзакцией после получения всей выборки. Частичный импорт при сетевой ошибке не выполняется.

Внешние запросы имеют timeout; редиректы отключены для защиты токенов и вебхуков. Сообщения об ошибках не включают URL вебхука, токен или тело ответа провайдера. Внешний HTML отображается как текст.

## Почтовая отправка

Отправка выполняется по ID сохранённого черновика. Сначала фиксируется состояние отправки, затем вызывается провайдер, после чего сохраняется итог. Повторный вызов для уже отправленного ID не отправляет повторное письмо. Неопределённый результат блокирует автоматический повтор. Атомарная транзакция между нашей БД и внешним почтовым сервисом невозможна, поэтому неопределённый результат требует сверки с провайдером.

Для production следующий шаг — transactional outbox, фоновые workers, provider draft IDs и reconciliation. Локальные `Reply` и `Forward` сейчас создают новое письмо с цитатой, а не сохраняют серверный threading `In-Reply-To`.

## Модульность

Настройки модулей хранятся на сервере. Отключение запрещает соответствующие операции приложения; `GET /api/state` скрывает данные отключённых функций и источников. Персональные задачи относятся к planner, командные — к backlog. Интеграции Jira/Битрикс24 управляются отдельно от отображения командного бэклога. Данные участников остаются справочником исполнителей для задач, даже если экран планирования команды отключён.

## Следующие архитектурные шаги

1. Подключить Битрикс24: чаты/сообщения, новости, подразделения/сотрудники, мероприятия. Задачи Битрикс24 исключены из области интеграции.
2. Ввести SQLite/PostgreSQL, миграции и пагинируемые API вместо полной загрузки состояния. Файловый BlobStore для IMAP уже добавлен.
3. Добавить аккаунты, роли, workspace isolation и OAuth для интеграций.
4. Расширить существующий IMAP worker на другие источники: очереди, delta tokens, архивирование исчезнувших записей, явные конфликты.
5. Нормализация сотрудников между источниками и учёт отпусков/праздников/частичной занятости.
6. Проверить IMAP на реальном ящике, добавить SMTP/OAuth, двусторонние папки и threaded conversations.

## IMAP worker

Подробный алгоритм и эксплуатация — [mail-sync.md](mail-sync.md). Worker принадлежит application, стартует в composition root и завершается по контексту процесса. Адаптер IMAP выдаёт порции через callback; приложение сохраняет оригиналы через BlobStore, затем одной транзакцией индекс и курсор. UI не управляет жизненным циклом worker. Пароли отсутствуют в domain/State и API.

## Почтовое хранилище и страницы

Рабочий composition root использует SQLiteRepository (modernc.org/sqlite, Go 1.25). Общий документ настроек/задач отделён от messages, threads, thread_folders, mail_refs, mail_files и FTS5. Письма, счётчики и IMAP-чекпойнты коммитятся одной транзакцией. Тела выбираются по ID, списки — по составному индексу (demo, folder, stamp, thread_id) с курсором. FTS5 поддерживает поиск по отправителю, адресатам, теме и тексту, включая старые сообщения цепочки. JSONRepository сохранён для небольших модульных фикстур и совместимости.

Первичная миграция JSON целиком атомарна, исходник сохраняется. Восстановление MIME/HTML из blob-оригиналов идёт идемпотентными порциями по 100 записей с сохранением локальных флагов. Вложения остаются в content-addressed mail-blobs; SQL содержит ссылки и индекс владельцев для проверки доступа к пересылке. Уже существующая SQLite не перезаписывается данными старого JSON при запуске.
