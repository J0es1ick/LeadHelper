# Почта и восстановление после простоя

Основной адаптер — IMAP поверх TLS (обычно порт 993). Нужны точное имя сервера, логин и пароль либо пароль приложения. Сервер берётся из настроек почтового провайдера/у администратора: MX-запись домена сама по себе не определяет IMAP. TLS проверяет сертификат и имя сервера; отключения проверки сертификатов нет.

## Настройка Windows

```powershell
.\scripts\configure-mail.ps1 -HostName '<подтверждённый IMAP-сервер>' -UserName 'you@company.ru'
.\scripts\stop.ps1
.\scripts\start.ps1 -Rebuild
```

Скрипт запросит пароль без отображения и сохранит его через Windows DPAPI в `data/imap-credential.xml`. Он расшифровывается только тем же пользователем на том же компьютере. Пароль не записывается в исходники или `.env`, не передаётся в браузер. `start.ps1` передаёт его процессу сервера через окружение и удаляет из окружения своего процесса после запуска. На сервере пароль остаётся в памяти до завершения процесса. Не включайте секреты в архивы проекта.

После настройки отключите деморежим в интерфейсе и сохраните настройки. Убедитесь, что модуль «Почта» включён. Можно нажать «Получить почту» сразу; иначе фоновый процесс проверит ящик в течение интервала.

Опциональный автозапуск при входе в Windows:

```powershell
.\scripts\install-autostart.ps1
```

Регистрация автозапуска выполняется только явным запуском этого скрипта. Она использует того же пользователя Windows и `start.ps1`, который не запускает второй экземпляр уже работающего сервера. До входа пользователя в Windows этот способ сервис не запускает.

## Docker

В `.env` задайте `MAIL_PROVIDER=imap`, `IMAP_HOST`, `IMAP_PORT=993`, `IMAP_USER`, `MAIL_SYNC_INTERVAL=60s`. Положите только пароль в `secrets/imap_password.txt` (каталог исключён из Git и Docker build context), ограничьте доступ к файлу средствами ОС и запустите:

```sh
docker compose -f compose.yaml -f compose.mail-secrets.yaml up -d --build
```

Compose монтирует файл как `/run/secrets/imap_password`, адаптер получает путь через `IMAP_PASSWORD_FILE`. Windows DPAPI-файл внутри Linux-контейнера не используется. Compose secrets в локальном режиме — файловое монтирование, а не шифрование файла на диске.

`restart: unless-stopped` поднимает контейнер после запуска Docker Engine, если он не был вручную остановлен. Автозапуск самого Docker Desktop/Engine настраивается отдельно в ОС. Volume `leadhelper-data` хранит индекс, прогресс и оригиналы писем. `docker compose down -v` удалит эти данные; для обычного перезапуска эта команда не нужна.

## Алгоритм

1. При старте сервер немедленно запускает worker. Браузер не требуется. В деморежиме, при отключённом модуле или отсутствии конфигурации подключений нет.
2. По умолчанию `LIST` перечисляет все доступные папки, затем `EXAMINE` открывает каждую только для чтения. Сначала загружается INBOX. `MAIL_FOLDERS=INBOX|Sent` может ограничить выборку точными именами папок.
3. Для каждой пары «аккаунт + папка» сохраняются `UIDVALIDITY` и последний обработанный `UID`. Поиск новых писем идёт по UID, а не по дате: старое письмо, добавленное во время простоя, тоже загрузится. Начальная синхронизация читает всю доступную историю без ограничения в 500 писем.
4. `BODY.PEEK[]` не отмечает письмо прочитанным на сервере. MIME разбирается в читаемый текст, вложения и метаданные. Кириллица и MIME-заголовки декодируются, HTML преобразуется в безопасный текст без загрузки изображений.
5. Исходный EML и вложения записываются в `data/mail-blobs/<hash-prefix>/<sha256>` с fsync перед фиксацией индексной записи. Каждые 10 писем (или в конце папки) сообщения и курсор сохраняются одной транзакцией индекса. Незавершённая порция после сбоя читается повторно. Записанный курсор не может указывать за сохранённую порцию.
6. При смене UIDVALIDITY папка перечитывается. Совпадение хеша исходного письма в той же папке и аккаунте переносит запись на новую эпоху без дубля, сохраняя локальные отметки и ID. Отдельные одинаковые копии с разными UID внутри одной эпохи остаются отдельными письмами.
7. При отсутствии сети worker повторяет попытки с увеличением интервала до 15 минут. Успешная проверка возвращает обычный интервал (по умолчанию 60 секунд). Один фоновый проход ограничен 5 минутами, ручной HTTP-вызов — 90 секундами; сохранённый прогресс продолжится в следующем проходе. Если другая IMAP-синхронизация уже выполняется, ожидание тоже учитывает отмену и срок запроса, не меняя состояние активного прохода.
8. Остановка сервера отменяет сетевые операции и сохраняет итог попытки. После аварийного завершения следующий запуск берёт курсоры с диска. Локальный сервер и контейнер используют тот же алгоритм.
9. Отказ сервера `NO`/`BAD` для отдельной папки не мешает чтению остальных. Итог попытки остаётся неуспешным и содержит название проблемной папки; её курсор остаётся на последней сохранённой порции. Полная успешная проверка не отмечается, пока ошибки остаются. Разрыв соединения, некорректный протокол и ошибка записи на диск останавливают текущий проход.

## Отображение и ограничения

- Интерфейс показывает текущую папку, число добавленных писем, последнюю полностью успешную проверку и ошибку последней попытки. При рабочем режиме открытый интерфейс обновляется раз в 10 секунд.
- INBOX → «Входящие»; Sent/Trash при наличии специального флага или распознанного имени → соответствующая папка. Остальные папки, включая серверные черновики, отображаются в «Архиве». В письме указано исходное название. Изменения папок, флагов и удаления на сервере не зеркалируются; это локальная копия поступающих писем.
- Локальное чтение/избранное/архив/корзина не меняют сервер. Повторная загрузка сохраняет локальные отметки. Удалённые на сервере письма остаются в локальной копии. Переименование папки может создать новую локальную копию её содержимого.
- Письмо до 25 МиБ загружается целиком. Для большего письма сохраняются заголовки с явным предупреждением; тело и вложения остаются на сервере. Экспорт такого письма содержит только полученные заголовки. Увеличение лимита и дозагрузка крупных писем — отдельный следующий шаг.
- Повреждённый MIME сохраняется оригиналом с предупреждением и не блокирует остальные письма. Оригинал доступен для выгрузки EML.
- Новые черновики, ответ и пересылка работают локально. Пересылка подставляет сохранённые вложения с проверкой доступа; общий лимит черновика — 5 МиБ/10 файлов. **Отправка через IMAP невозможна; SMTP ещё не подключён.** Нажатие отправки возвращает понятную ошибку и сохраняет редактируемый черновик. Никакой автоматической отправки нет.
- JSON-индекс и полная загрузка состояния подходят для текущего однопользовательского контура. Вложения вынесены в файлы, но текст писем ещё в индексе. Для больших корпоративных архивов нужны SQLite/PostgreSQL, пагинация и полнотекстовый индекс. Сборка мусора неиспользуемых blob-файлов пока не реализована; резервировать надо весь `data`/volume, а не только JSON.

## Что проверено

Контрактные тесты используют изолированный IMAP-сервер на `net.Pipe`: разрыв после сохранённой порции, продолжение по UID, обратный диапазон `N:*`, смена UIDVALIDITY, посторонний untagged FETCH, повреждённый MIME, границы парсера и modified UTF-7. Прикладные тесты переоткрывают файловый репозиторий, проверяют сохранность курсора/оригинала/вложения, отсутствие дублей, локальные отметки, отключение модуля и завершение worker.

Дополнительно 7 ноября 2026 воспроизведены и исправлены блокировка остальных папок при отказе `EXAMINE`/`FETCH` и ожидание занятой синхронизации после истечения срока запроса. Проверено, что ошибка сохранения останавливает проход и передаётся вызывающему коду. `go test -race ./... -count=1`, `go vet ./...` и production-сборка фронтенда прошли. Локальный сервер пересобран с IMAP-адаптером; SHA-256 файла данных до и после перезапуска совпал.

Проверка реального ящика 7 ноября 2026 не дошла до авторизации: исходящее сокетное соединение было запрещено средой (`WinError 10013`). Пароль не проверен, содержимое ящика не получено. Точное имя IMAP-сервера ещё должно быть подтверждено. Не считать результаты фикстур подтверждением рабочего подключения.
